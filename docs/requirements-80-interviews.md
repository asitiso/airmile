# 대한항공·아시아나항공 마일리지 보너스 항공권 통합 검색
## 최종 개발 설계서 v1.0 — 80개 인터뷰 확정본

- **기준일:** 2026-10-26 (대한민국)
- **대상:** 본인 1인용, PC·모바일 겸용 웹 프로그램
- **결정 상태:** 인터뷰 1~80 종료, 인터뷰 80=B(웹사이트 + GitHub + 간단한 관리화면)
- **문서 구분:** 구현 요구사항은 확정. 항공사 실좌석 자동 데이터 획득 가능성은 기술 검증 전이며 확정되지 않음.
- **가장 중요한 원칙:** 실제 예약 가능한 *마일리지 보너스* 좌석을 최대한 빠르게 표시한다. 12개월을 전부 조회하느라 첫 결과가 느려져서는 안 된다.

## 1. 실행 요약

### 1.1 사용자가 얻어야 하는 결과

1. 대한항공 스카이패스 및 아시아나 마일리지(합병 후 구 아시아나 마일리지 포함)의 **실제 발권 가능한 보너스 좌석**을 프로그램별로 비교한다.
2. 편도·일반 왕복·기간 왕복을 구분한다. 출발·귀국 모두 **요일이 맞는 7열 달력**으로 표시하며, 월간 상세 보기와 12개월 연간 보기를 제공한다.
3. 날짜별로 항공사와 사용 마일리지 프로그램, 이코노미·비즈니스·일등석, 조회된 항공편 수, 최저 필요 마일리지를 표시한다. 상세 패널에서 조회된 **모든 항공편**을 스크롤하여 볼 수 있다.
4. 사용자가 지정한 출발일과 앞뒤 3일을 최우선 처리하고, 첫 1개월을 먼저 채운다. 나머지 11개월은 속도에 여유가 있을 때만 갱신한다.
5. 조회 시점·공식 확인 여부·인원 가능 여부·검색 완료 범위를 숨기지 않는다. 검색 실패·미조회·예약 오픈 전과 좌석 없음은 서로 다르게 표시한다.
6. 관심 좌석 알림·즐겨찾기·예약 페이지 이동·항공편 비교·클라우드 백그라운드 작업을 지원한다.

### 1.2 성능 목표(실측 전 확정 보장 아님)

| 항목 | 목표 | 측정 방식 |
|---|---|---|
| 저장된 달력 표시 | 2초 이내 | 인증 후 캐시 존재 조건, p95 |
| 신규 검색 첫 실제 항공편 표시 | 10초 이내 | 최초 유효 데이터를 수신한 시간, p95 |
| 첫 1개월 조회 | 가능한 한 신속하게 | 항공사·노선·인원·좌석등급별 별도 측정 |
| 12개월 화면 | 즉시 접근 | 데이터 미조회 날짜도 캘린더에는 표시 |
| 날짜 변경·필터 | 이미 저장된 데이터는 즉시 반영 | 새 항공사 조회 없이 클라이언트/서버 캐시 계산 |
| 항공편 누락 | 지원하는 데이터 소스의 조회 범위 내에서 누락 0 목표 | 공식 예약 화면/원본 응답과 원본 결과 대조 |

> '모든 항공편'은 **접근·조회가 실제 검증된 데이터 제공 범위 내의 모든 선택지**라는 의미다. 항공사 전체 보너스 재고를 제공하지 않는 공급자만 연결된 상태에서는 전 항공편 완전성을 주장하지 않는다.

## 3. 화면·사용자 흐름

### 3.1 메인 화면

- 첫 줄: `편도 | 일반 왕복 | 기간 왕복` 전환.
- 필수 입력: 출발지(기본 인천), 최대 10개 목적지, 출발 기준일, 탑승 인원(1~4), 검색 버튼.
- 검색 옵션: 우선 조회 1·3·6·12개월, 사용자 지정 우선 좌석 등급(E/B/F).
- `상세 설정` 접기 안에 제휴편·분리발권·공항이동·어린이 동반·경유시간·시간대·요일 필터.
- 최근 검색·즐겨찾기·마지막 조건 복원.

### 3.2 연간·월간 달력

- 실제 요일이 맞는 **일~토 7열 달력**. 12개 월별 달력을 제공하며 `연간`과 `상세 월간` 전환.
- 모든 날짜 칸에 대한항공/아시아나 운영편과 **차감 마일리지 프로그램**의 차이를 식별할 수 있게 표시.
- 3개 등급별 조회된 항공편 건수/최저 마일리지와 출처 확인 상태 표시. 데이터 미조회인 칸은 `미조회`로 유지.
- 모바일 월간 달력은 가독성을 위해 가로 스크롤. 항공편 상세는 아래에서 열리는 패널.
- 필터로 0편이 된 날짜는 매진으로 오인되지 않도록 `필터 일치 0편`으로 표시.
- 상단에 데이터 갱신 시각과 검색 처리 중인 구간 표시.
- 선택된 출발일 주변 ±3일을 먼저 채운다. 목적지 여러 개일 때는 라운드로빈 조회.

### 3.3 왕복 두 방식은 서로 독립

- **일반 왕복:** 출발일 및 귀국일을 직접 선택. PC에서는 두 달력을 좌우에, 모바일에서는 탭으로 표시. 출발·귀국 항공사/좌석 등급이 서로 달라도 됨.
- **기간 왕복:** `출발 가능 범위`, `여행 7~10일`, 여행 일수 계산 기준(출국일 또는 현지 도착일), 출발/귀국 요일을 설정. 확보된 편도 결과를 조합해 조건 일치 날짜를 달력에 강조. **검색된 나머지 날짜는 절대 숨기지 않음.**
- 오픈조 가능: 인천→파리 / 로마→인천. 별개 항공사/프로그램이면 구간별 별도 발권 가능성을 표시하고 합산 마일리지는 마일리지 프로그램별로 따로 나타냄.
- 여정별 세금 및 유류할증료는 확인된 통화로 표시. 값이 없으면 `확인 필요`.

### 3.4 항공편 목록과 비교

- PC 우측 상세 패널, 휴대폰 하단 패널.
- 개별 항공편에는 출발·도착 공항, 편명, 운영 항공사, 차감 마일리지 프로그램, 날짜·현지시간, 소요시간, 환승 장소·시간, 구간별 좌석 등급, 필요 마일리지(1인/총 인원), 세금, 인원 확인 상태, 공식 확인 상태, 원본 데이터 시각을 표시.
- 날짜별 전체 검색 결과는 가상 스크롤로 렌더링. 정렬과 필터는 기존 데이터를 재사용.
- 관심 항공편 저장 및 비교, 매진 후에도 카드 유지, 비교 화면 열 때 최신 상태 재확인.
- 예약 이동 시 공식 목적지 웹사이트를 열고 허용된 범위의 검색 조건만 전달; 필요한 조건은 한 번에 복사.

### 4.1 핵심적인 데이터 구분

1. `operating_carrier`: 항공기를 실제 운항하는 항공사 (KE/OZ 등).
2. `marketing_carrier/flight_number`: 판매·편명상 항공사. 합병으로 변경될 수 있음.
3. `redemption_program`: 실제 차감되는 마일리지 프로그램 (`SKYPASS`, `LEGACY_ASIANA` 또는 기타 제휴 프로그램).
4. `award_fare_class`: 일반 항공권이 아닌 보너스 예약 클래스.
5. `program_bookable`: 해당 **보유 프로그램 마일리지로 발권 가능한지** 확인 상태.

제휴 마일리지로 조회되는 KE 운항편을 곧바로 **SKYPASS로 예약 가능**하다고 표시하는 것은 금지.

### 4.2 2026년 12월 17일 통합 대응

- 해당 날짜부터 기존 아시아나편이 KE 편명으로 전환되므로 운항 항공사·편명만으로 SKYPASS와 구 아시아나 마일리지 잔액을 합쳐서는 안 된다.
- **기존 아시아나 마일리지는 10년간 별도 관리·사용**된다는 공식 공지를 적용한다.
- 보너스 좌석 검색 시 `SKYPASS`, `구 아시아나 마일리지` 프로그램별 예약 조건/공제량/가능 상태를 보존한다.
- 출발일과 예약일에 따라 이용 가능한 공식 예약 사이트·프로그램이 달라지므로 규칙을 날짜 버전으로 관리한다.
- 합병 이후 첫 배포/변경 시 이전·이후 날짜와 KE/OZ 편명 매핑 회귀 테스트를 실시한다.

### 4.3 예약 가능한 날짜 범위

- 대한항공 공식 안내: 보너스·일반 항공권 모두 출발 **360일 전 오전 9시 KST**부터 예약 가능(조회 기준 날짜가 아니라 출발일에 따라 처리).
- 따라서 12개월 캘린더의 끝 일부는 `예약 오픈 전`일 수 있다. 아시아나 및 통합 이후 규정은 해당 시점의 공식 정책으로 별도 검증.
- **예약 오픈 전/미조회/결과 없음/조회 실패/지원 안 됨/검증 필요** 상태를 별개로 관리한다.

### 4.4 아직 실행하지 않은 실제 API 테스트

- 이번 조사로 사용자용 공식 좌석 캘린더와 외부 서비스의 문서상 지원 범위는 확인했다.

## 5. 권장 시스템 구성

### 5.1 최소 구성부터 시작

```text
[PC/모바일 웹 브라우저]
    | Google OAuth (허용 이메일 1개)
    v
[Next.js / React 프론트 + 읽기용 API]
    | ① 캐시 결과 즉시 응답  ② 검색 작업 등록
    v
[PostgreSQL: 검색 작업·결과·사용자 환경설정·알림]
    ^                 |
    | 저장            | 대기 작업 예약/우선순위 변경
    |                 v
[서버 백그라운드 Worker / 작업 큐]
    | 항공사/허용된 데이터 제공자 어댑터
    v
[공식 또는 적법한 외부 보너스 좌석 공급자]
```

- **프론트엔드:** Next.js + TypeScript, 모바일 반응형, 7열 월간 캘린더(접근성·키보드 지원 포함).
- **데이터베이스:** PostgreSQL(관리형), 사용자·검색 작업·항공편·원본 증거·알림 관리.
- **백그라운드:** 데이터 소스가 확정되면 지속 작업이 가능한 Worker를 배포. 단기 실행 제약이 있는 웹 호스팅 기능만으로 12개월 장기 검색을 무리하게 구현하지 않음.
- **작업 큐:** 초기에는 PostgreSQL 기반 큐로 충분. Redis·다중 서버·복잡한 이벤트 시스템은 실제 병목이 측정되기 전에는 도입하지 않음.
- **반영 방식:** SSE 또는 짧은 폴링으로 날짜별 업데이트 표시. 인증·네트워크 환경상 불가능한 방법은 대체 수단 사용.
- **배포:** GitHub 개인 저장소(비공개 기본), 프론트엔드·API·worker의 오류 로그를 확인하는 최소 관리자 화면. 배포 대상 서비스는 비용과 워커 지원 여부 검증 후 선택.

### 5.2 검색 작업 우선순위

| 우선순위 | 대상 | 조건 |
|---:|---|---|
| P0 | 현재 클릭한 날짜/월, 필수 귀국 구간 | 신규 요청 시 즉시 대기열 앞으로 이동 |
| P1 | 선택한 출발일 ±3일 | 가능한 데이터 소스별 배치 조회 우선 |
| P2 | 선택한 출발일부터 첫 약 1개월 | 여러 목적지를 골고루 채움 |
| P3 | 사용자가 선택한 3·6·12개월의 나머지 날짜 | 검색 성능이 양호할 때 순차 처리 |
| P4 | 별도 관심이 없는 오래된 기간/이전 검색 | 속도 부담이 있으면 지연 또는 일시정지 |

- 동일한 요청은 중복 등록하지 않고 현재 작업에 합류(single-flight).
- 캐시가 존재하면 즉시 보여주고 재검증은 큐로 넘긴다(stale-while-revalidate).
- 새 노선 검색 시 오래된 작업은 저장한 뒤 안전한 지점에서 일시정지.
- 모든 항공사 호출에 공급자별 허용 동시성, 쿼터, `Retry-After`, 유한 횟수 지수 백오프, 회로 차단 적용.
- 예약 자격 검증과 선택 날짜 조회가 지연되면 P3/P4 자동 중단.
- **직항 먼저**는 호출 수·총 지연이 실제 감소한 소스에서만 적용. 한 번 조회로 직항·경유편 모두 얻을 수 있으면 추가 분할 금지.

### 5.3 자동 갱신 및 일시정지

- 관심 날짜: 목표 2~4시간 간격. 나머지: 하루 갱신 목표. 단, 허용 조회량을 초과하면 빈도를 낮춘다.
- 백그라운드 작업은 웹 창 종료와 독립적이고 재시작 가능한 형태로 관리.
- 중지/재개 시 완료 데이터 유지, 미완료 작업부터 진행.
- 날짜·객실 등급·목적지·운항/차감 프로그램이 변경되면 올바른 캐시 키를 사용해 재사용/재조회 여부 판별.

### 6.2 항공편 기본 데이터 계약(예시)

```ts
type Program = 'SKYPASS' | 'LEGACY_ASIANA' | 'PARTNER_OTHER';
type Cabin = 'ECONOMY' | 'BUSINESS' | 'FIRST';
type VerifyStatus =
  | 'OFFICIAL_CONFIRMED' | 'THIRD_PARTY_UNVERIFIED'
  | 'PASSENGER_COUNT_UNVERIFIED' | 'WAITLIST_ONLY'
  | 'SOLD_OUT_CONFIRMED' | 'NOT_YET_OPEN'
  | 'NOT_CHECKED' | 'CHECKING' | 'ERROR' | 'UNSUPPORTED';
type Completeness = 'COMPLETE_WITHIN_SOURCE' | 'PARTIAL' | 'UNKNOWN';

type AwardOffer = {
  id: string;
  redemptionProgram: Program;
  operatingCarriers: string[];
  marketingFlightNumbers: string[];
  origin: string; destination: string;
  departureLocal: string; arrivalLocal: string;
  segments: Array<{
    flightNumber: string; operatingCarrier: string;
    origin: string; destination: string;
    depLocal: string; arrLocal: string;
    cabin: Cabin; awardBookingClass?: string;
  }>;
  requestedPassengers: number;
  confirmedPassengers?: number;
  milesPerPassenger?: number;
  totalMiles?: number;
  taxesAndFees?: { amount: number; currency: string };
  ticketing: 'THROUGH_TICKET' | 'SEPARATE_TICKETS' | 'UNKNOWN';
  verifyStatus: VerifyStatus;
  completeness: Completeness;
  sources: Array<{ provider: string; checkedAt: string; sourceId: string }>;
  officialBookingUrl?: string;
};
```

- *날짜 기반 조회 캐시 키*는 차감 프로그램, 노선, 실제 날짜, 요청 인원, 자녀 구성, 좌석 등급 범위, 경유/분리발권, 소스 버전까지 구분한다.
- *중복 제거*는 **운항 세그먼트 묶음 + 출발 시각 + 차감 마일리지 프로그램 + 발권방식 + 구간별 등급 + 예약 조건**을 기준으로 한다. 서로 다른 가격·소스 확인 상태는 근거로 보존한다.
- 항공편 건수와 잔여 좌석 수는 별개. 응답에서 좌석 수를 제공하지 않으면 `확인 불가`, 결코 0석으로 변환하지 않는다.
- `COMPLETE_WITHIN_SOURCE`는 **그 제공자 안에서 페이지네이션 및 해당 요청이 완료**된 뜻일 뿐, 시장 전체 마일리지 재고의 완전성을 뜻하지 않는다.

```text
GET  /api/favorites                     저장 노선·관심 항공편
```

> 화면의 가상 스크롤과 서버의 커서 기반 전체 항공편 조회를 같이 사용한다. 실제 공급자 자체가 상위 n개만 주는 경우 `불완전한 결과` 경고를 제거할 수 없다.

## 7. 실제 데이터 조회 검증 계획 (기술 검증 게이트)

### Gate 0 — 출처·권한 확인

1. 대한항공/아시아나 공식 개발자·파트너 데이터 제공 가능 여부와 약관을 확인한다.
2. 두 회사의 **자체 마일리지 프로그램 기준** 잔여 좌석, 1~4명 확인, 월간 캘린더, 항공편 상세 결과, 세금/유류할증료, 대기예약 여부를 구분해서 지원 여부 문서화한다.
3. 외부 서비스도 프로그램별 지원 목록, 유료/무료 사용 권한, 개인 프로그램 임베딩/서버 사용 허용, 호출 제한을 확인한다.
4. 지원하지 않는 프로그램을 지원하는 것처럼 대신 처리하지 않는다. 동적 좌석 조회를 자동화할 권한이 없다면 명시하고 합법적인 공급자나 공식 수동 재확인 흐름을 설계한다.

**통과 조건:** 최소 한 가지 데이터 제공자가 해당 보유 마일리지로 발권 가능한 보너스 좌석을 인증 가능하고 허용된 방법으로 조회할 수 있다는 증거 확보.

### Gate 1 — 3개 노선 비교표 작성

검증 노선: **ICN→TYO(도쿄), ICN→NYC(뉴욕), ICN→PAR(파리)**. 각각 대표 공항을 실제 조회 대상 공항으로 명확히 펼친다.

- 선택 출발일 기준 첫 30~31일. 1명과 2명, 이코노미/비즈니스/일등석(실제 운항 등급만), 직항과 경유 1회.
- 통합 이후 적용 시점을 고려하여 2026-12-17 전·후 날짜를 반드시 포함.
- 샘플 날짜를 우선 측정 → 한 달 조회 → 원본과 프로그램 DB 대조.
- 공식 화면과 데이터 공급자의 `프로그램/날짜/구간/편명/인원/좌석/마일리지/세금` 일치 여부 조사.
- 각 소스마다 몇 개 요청/초, 최초 결과 초, 월간 완료 분, 제한 오류 비율, 일 단위 0/부분 응답 비율 기록.
- 한 날짜에 항공편 2개 이상이 존재하는 사례, 경유편, 혼합 등급, 2명 미확인 사례를 수집하고 재현 테스트.

**통과 조건:** 실제 공식 예약 경로와 일치하는 좌석을 검증하고, 데이터 누락·지원 안 되는 항목의 범위를 수치화할 것. 데이터가 없으면 공식 예약과 다르다고 단정하지 말고 `미조회/미지원`으로 기록.

### Gate 2 — 응답 성능 실측

- 저장된 달력 렌더링 p50/p95, 신규 검색 첫 유효 항공편 p50/p95를 최소 10회 반복해 기록.
- 단일 목적지와 3·10개 목적지, 1/2명, 최초 캐시 없음/이미 조회함, 공식 소스 정상/429 제한 상황 각각 테스트.
- 백그라운드 조회 OFF vs ON 조건에서 사용자가 클릭한 달 결과 시간 비교. 백그라운드 ON이 전면 검색을 의미 있게 지연시키면 자동 감속.
- 동일한 날짜를 10회 클릭해도 실제 서버 요청 수가 무한 증가하지 않는지 확인.
- 2초/10초 미달 시 API 공급자 시간인지 렌더링 시간인지 분리하여 원인 진단.

### Gate 3 — 데이터의 완전성·최신성·보안

- 동일 예약 선택지는 한 번만 카운트, 서로 다른 마일리지 프로그램은 분리.
- 비즈니스 2명 미확인 vs 확정 가능 상태 구분.
- `검색 완료`도 데이터 소스 범위 및 대상 등급을 명시.
- 저장된 결과는 항상 조회 시각을 제공하고 오래된 결과를 최신이라 속이지 않는다.
- 구글 이메일 allowlist, 비밀키 서버 보관, 로그인 실패 감사 로그, 푸시 중복·서버 재시작 복구 테스트.

### 8.2 기능별 필수 테스트(수락 기준)

1. 편도 날짜 클릭 시 해당 일자의 저장 항공편 즉시 표시 및 재확인.

5. 검색 기준일의 ±3일을 우선하고 첫 1개월을 나머지 기간보다 먼저 조회.

## 9. 구현 원칙·비용·운영 의사결정

- **추가 유료 결제 자동 실행 금지.** 무료 우선, 외부 서비스/API/호스팅 과금은 실제 혜택과 비용 비교 후 명시적인 승인 받아 진행.
- 개인 전용으로 Google OAuth 1인 allowlist; 항공사 비밀번호 저장을 기본으로 요구하지 않음.
- 기술 선택은 `기존 방식보다 실제 시간이 얼마나 단축되는가`를 우선. 날짜 클릭 시 재조회 등 반복 검색을 줄이는 기능은 포함하고, 자동화가 더 느리거나 자주 고장 나면 제외/유예.
- 먼저 기술 검증을 완료하고 소스와 권한을 확정한 뒤 UI 구조를 연결한다. 데이터 품질 증거가 없으면 달력에 가짜 실제 예약 좌석을 넣지 않는다.
- 웹사이트의 선불/발권 기능은 만들지 않으며 공식 항공사 웹사이트로 이동하여 예약한다.
- 전체 결과가 불완전하면 화면에 누락 가능성을 설명하고, '검증된 범위의 전체 목록'까지만 약속한다.

## 10. Codex 개발 인수인계 명령문

> 이 문서를 프로그램의 단일 요구사항 기준(Single Source of Truth)으로 삼아라. 80개 인터뷰의 기능을 임의로 삭제하거나 단순화하지 말고, 0단계인 **대한항공 SKYPASS/구 아시아나 마일리지 자체 프로그램의 실제 보너스 좌석 데이터를 허용된 경로에서 읽을 수 있는지**부터 검증하라. 다른 항공사의 제휴 마일리지 검색 결과를 SKYPASS/구 아시아나 발권 재고로 간주하지 말 것. 진행 단계마다 측정 자료와 화면·코드 테스트를 남겨라. 조회 불가능한 항목은 '확인 불가'로 드러내고 무한 재시도·사이트 보호장치 우회·거짓 좌석 데이터를 금지한다. 기술 검증을 통과하면 PostgreSQL 기반 캐시/작업 큐 + React 7열 달력 + 구글 개인 로그인 + 가상 스크롤 상세 패널을 구현하라. 사용자에게 속도와 정확성 기준 미달 부분을 명시하라. 최종 결과는 GitHub 비공개 저장소와 실제 접속 가능한 PC/모바일 웹사이트, 검색 관리자 화면으로 제공할 계획을 수립하되, 외부 계정 연결이나 비용 지불 전에는 사용자 승인을 받는다.
